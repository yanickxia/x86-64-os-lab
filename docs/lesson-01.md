# 第 1 课：观察 CPU 复位现场

## 本课只回答一个问题

x86-64 CPU 复位后，执行自己取到的第一条指令时，究竟处于什么状态？

先不写启动代码，也不接受“手册说是这样”作为唯一证据。我们让 QEMU 在第一条指令之前暂停，再用 GDB 检查寄存器和内存。

## 先修知识：如何阅读 CR0

实验会读取 `RIP`、`CS` 和 `CR0`。这一课暂时只看 `CR0` 的两个 bit：

- `PE` 是 bit 0；为 1 表示启用保护模式。
- `PG` 是 bit 31；为 1 表示启用分页。

判断某个 bit 时不要靠目测十六进制，可以计算：

```text
(CR0 >> bit_number) & 1
```

QEMU 的 `-S` 会让 guest 在第一条指令执行前暂停；GDB 随后读取的是复位现场，而不是已经运行过一段 BIOS 的状态。此处只讲观察方法，不提前公布寄存器的真实值。

## 运行实验

打开第一个终端：

```sh
cd /Users/yanick/codes/mine/operating-system/x86-64-os-lab
make qemu-reset
```

`-S` 让 QEMU 在 CPU 执行第一条指令前暂停，`-gdb tcp::1234` 暴露调试端口。

保持它运行，再打开第二个终端：

```sh
cd /Users/yanick/codes/mine/operating-system/x86-64-os-lab
make inspect-reset
```

把输出中的寄存器值、16 字节机器码和第一条反汇编指令记录下来。检查完成后，在第一个终端按 `Ctrl-C` 停止 QEMU。

这里由 GDB 读取寄存器和原始字节，再由 `ndisasm -b 16` 解码指令。QEMU 的调试接口会把 CPU 报告为 x86-64，如果直接让 GDB 使用 64 位规则反汇编复位点，正确的 16 位指令可能显示成 `(bad)`。原始字节没有错，错的是解释字节时采用的模式。
