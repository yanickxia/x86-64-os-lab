# 第 15 课：复盘 —— 交给 C 之前，这台机器处于什么状态

## 本课不引入新机制

前 14 课全部落在同一个轴上：机器是怎么工作的。每一课的产出都是"把某一位设成 1""按硬件规定的格式建一张表""按固定的寄存器契约调一个固件服务"。这确实像照着手册实现功能——因为从 CPU 复位走到 long mode，这条路上的设计自由度很少。要可靠访问 1 MiB 以上的物理内存，必须先处理 A20；GDT 的编码格式由硬件规定；`CR4.PAE → CR3 → EFER.LME → CR0.PG` 的依赖顺序也不能随意交换。

但这 14 课里其实已经做了一批**真正有取舍的决策**，只是课程替你悄悄做掉了，从没作为决策摆出来讨论。这一课把它们翻出来。

本课不写一条 guest 指令，不加一个 CPU 机制，也不设置红灯、绿灯或新的验收命令。它只把前 14 课散落的机制串成一条完整主线，并把即将交给 C 的机器状态讲清楚。第 16 课先横向比较 x86-64、RISC-V 与 ARM64，第 17 课再开始引入 C；此后讲义会常驻四个栏目：OS 视角、对照实现、设计题、配套阅读。

## 本章怎么读

先顺着 §1 的执行路径把代码重新连起来，再看 §2 的最终状态。§3 解释课程替你做过的设计选择，§4 说明为什么“已经进入 long mode”仍不等于“已经有可用内核”。最后用 §5–§8 把这些硬件机制映射到后续操作系统主题。这里不要求背完整寄存器值，也不要求逐题作答。

## 1. 完整路径：从复位到载荷执行

按真实执行顺序，不是按课程编号。注意 `load_kernel` 在 `main` **之前**执行——`start` 在 `0x7c0d` 调用它，返回后才落到 `0x7c10`。

| # | 位置 | 谁在执行 | 模式 | 这一步改变了什么 | 取证 |
|---|---|---|---|---|---|
| 1 | `0xfffffff0` | CPU | 16 位实模式 | 复位向量；`CR0.PE=0`、`CR0.PG=0` | `make inspect-reset` |
| 2 | `0xf000:0xe05b` | BIOS | 16 位实模式 | 建 IVT、自检、挑启动设备 | 第 1 课的 `jmp far` |
| 3 | `0x0000:0x7c00` | BIOS→我们 | 16 位实模式 | 512 字节搬到 `0x7c00`，`DL`=启动盘号 | `make check-boot` |
| 4 | `0x7c00 start` | 我们 | 16 位实模式 | `DS=ES=SS=0`、`SP=0x7c00` | `make check-segments` |
| 5 | `0x7d50 load_kernel` | 我们 + BIOS | 16 位实模式 | `INT 13h` 把 LBA 1 读到 `0x10000` | `make check-kernel-load` |
| 6 | `0x7c10 main` | 我们 | 16 位实模式 | 开 A20；`LGDT` 装 GDTR；输出 `Hello` | `check-a20`、`check-gdt` |
| 7 | `0x7c70` | 我们 | 16 位 → 32 位 | `CLI`；`CR0.PE=1`；far jump 到 selector `0x08` | `make check-protected` |
| 8 | `0x7c90` | 我们 | 32 位保护模式 | `DS=ES=SS=0x10`、`ESP=0x90000`；输出 `P` | `make check-protected` |
| 9 | `0x7cb0` | 我们 | 32 位保护模式 | 清零并连接 PML4/PDPT/PD；输出 `T` | `make check-page-tables` |
| 10 | `0x7cf0` | 我们 | 32 位 → 64 位 | `CR4.PAE`、`CR3`、`EFER.LME`、`CR0.PG`；far jump 到 `0x18` | `make check-long-mode` |
| 11 | `0x7d30` | 我们 | 64 位 long mode | 输出 `L`；绝对间接跳转到 `0x10000` | `make check-kernel-entry` |
| 12 | `0x10000` | 载荷 | 64 位 long mode | 短跳过 magic；输出 `K`；死循环 | `make check-kernel-entry` |

三次控制权移交值得单独记住，它们的性质完全不同：

- 第 3 步是**固件交给我们**，靠的是磁盘上第 510 字节起的 `0xaa55` 约定。
- 第 7、10 步是**我们交给我们自己**，但换了执行模式，靠 far jump 重载 `CS`。
- 第 11 步是**我们交给独立编译单元**，`CS` 不变，靠绝对间接跳转和 linker script 定下的地址契约。

## 2. 交给 C 前，哪些状态已经成立

不必背完整寄存器值；先记住每项状态解决了什么问题。

| 维度 | 当前状态 | 它意味着什么 |
|---|---|---|
| 执行模式 | long mode、ring 0，`CS=0x18` 指向 64 位代码段 | CPU 已经按 x86-64 指令语义执行 |
| 分段 | GDT 已加载，代码和数据段都是 base 0 的平坦段 | 逻辑地址到线性地址基本不再平移，隔离交给分页 |
| 分页开关 | `CR0.PE/PG=1`、`CR4.PAE=1`、`EFER.LME/LMA=1` | 保护模式、四级分页和 64 位模式都已生效 |
| 页表根 | `CR3=0x1000` | PML4 位于物理地址 `0x1000` |
| 当前映射 | 低 2 MiB 使用一个 2 MiB large page 恒等映射 | boot code、页表、内核载荷和当前栈都能继续按原地址访问 |
| 内核载荷 | raw bytes 已读到 `0x10000`；ELF `.text`、entry 和 symbol 地址也从 `0x10000` 开始 | 加载地址、链接地址和跳转目标一致 |
| 栈 | `RSP=0x90000`，向低地址增长 | 已经能执行 `call/ret`，但没有边界和保护页 |
| 中断 | `IF=0`，IDTR 仍指向复位后的实模式 IVT | 当前只是“暂时没触发异常”，还没有可用的 long-mode IDT |
| 输出 | 只能通过 QEMU/Bochs debugcon `0xe9` 输出 | 适合教学取证，但还不是真实设备驱动 |

把这张表压缩成一句话：**启动代码已经提供了一个能执行 x86-64 指令、能访问低端内存、能跳入独立 ELF 载荷的 ring-0 环境，但异常处理、可靠内存管理和正式设备支持都还不存在。**

## 3. 课程替你做掉的七个设计决策

每条都按同一格式：**约束是什么 → 反过来选会崩在哪 → 真实系统怎么做**。

### 3.1 载荷为什么放 `0x10000`

约束来自当前 BIOS 磁盘服务的接口：`INT 13h AH=02h` 用实模式 `ES:BX` 指定缓冲区。我们希望在尚未主动开启 A20 的阶段，选择一段确定可达、不会覆盖 boot sector 或 BIOS 数据的低内存。`0x10000 = 0x1000:0x0000`，恰好是 64 KiB 边界，算术和分块读盘都很干净。

同时要避开低内存里已经被占用的区域：`0x0`–`0x4ff` 是 IVT 和 BIOS 数据区，`0x7c00`–`0x7dff` 是我们自己，`0x9fc00` 起是 EBDA，`0xa0000` 起是显存。`0x10000` 落在中间那段安全空洞里。

反过来选：`0x100000` 并非在算术上绝对无法表示；A20 已开启时，`FFFF:0010` 可以形成这个地址。但当前读盘发生在课程主动开启 A20 之前，不能把 A20 已开启当作可靠前提，关闭时该地址会回绕到 0。`0x7e00` 也能工作，但它紧贴 boot sector，把载荷缓冲区与以后可能增长的 bootloader 耦合在一起；`0x10000` 留出了清晰边界。

真实系统通常仍采用分阶段加载：先把足够的 loader 放进可靠的低内存，再处理 A20、模式切换和更完整的磁盘访问，最后把内核放到 1 MiB 以上。这主要是为了摆脱早期 BIOS 接口、内存布局和缓冲区边界的组合限制，而不是因为 `segment × 16 + offset` 在算术上绝对到不了 1 MiB。

### 3.2 为什么用 2 MiB large page，而不是 4 KiB 页

4 KiB 粒度需要第四级页表 PT，要覆盖 2 MiB 得填 512 个 entry；2 MiB large page 只需在 PD[0] 置 `PS=1`，一个 entry 搞定。启动扇区总共只有 512 字节，这个差别是决定性的。

代价是粒度：一个 2 MiB 页只能有一套权限位。想让 `.text` 只读、`.data` 不可执行（NX），必须换成 4 KiB 页。所以这是个**临时**决定，真内核后期一定要改。

反过来选：改成 4 KiB 却忘了填 PT。硬件走到 PD 发现 `PS=0`，就会把 entry 里的地址当作 PT 的物理基址继续往下走一级，读到的是**那一页当时恰好是什么**。

这里要小心，不能假设它是零。`setup_page_tables` 只清零了三页：

```asm
PAGE_TABLE_DWORDS equ (3 * 4096) / 4      ; 只覆盖 0x1000..0x3fff
```

第四级 PT 需要第四页（比如 `0x4000`），而它从来没被我们清零过。在当前 QEMU 上 `xp /4gx 0x4000` 确实全是零，于是 `P=0` → `#PF` → 没有可用 IDT → `#DF` → triple fault，现象是"什么都没输出就重启了"。但这个零是 QEMU 的 RAM 初始状态给的，不是我们做的——正如第 11 课 §4.5 强调过的那样，不能把偶然状态写进假设。

如果那一页残留的字节里 bit 0 恰好是 1，后果反而更糟：硬件会把它当成一个合法 PTE，映射到一个错误的物理帧，然后**安静地**在错误内存上继续取指或读写。没有异常、没有重启，只有难以定位的行为异常。所以"忘了清零页表"这类 bug 里，崩掉是幸运情况。

真实系统：Linux 的 `arch/x86/kernel/head_64.S` 早期恒等映射同样用 2 MiB 页，正式映射建好后再换。JOS 的 `entrypgdir` 用 4 MiB 页（32 位 PSE），同样的思路。

### 3.3 为什么必须恒等映射，不能直接跳高半区

这是整条路径上最容易想错的一步。关键在于：`mov cr0, eax` 打开 `CR0.PG` 的**下一条指令的取指**就已经要经过页表了。CPU 不会等你跳转，它立刻用当前 `RIP` 去查表。

当前 `RIP` 在 `0x7cxx`。所以 `0x7cxx` 这个线性地址在开启分页的那一瞬间就必须已经映射到物理 `0x7cxx`。恒等映射的作用不是"方便"，而是保证"开分页前后同一个地址指向同一块内存"，让这次切换在指令流上是无缝的。

反过来选：只建高半区映射（比如只映射 `0xffffffff80000000`）。`mov cr0, eax` 执行完，CPU 取下一条指令，线性地址 `0x7cxx` 查表发现 `P=0` → `#PF` → 没有 IDT → `#DF` → triple fault。崩点精确到那一条 `mov cr0, eax` 的**下一条**指令。

真实系统：高半内核的标准做法是**两套映射同时存在**一段时间。JOS 的 `entrypgdir` 同时映射 `[0, 4MB)` 和 `[KERNBASE, KERNBASE+4MB)`，都指向物理 `[0, 4MB)`；开分页后仍在低地址运行，跳到高地址，再把低地址映射拆掉。我们现在只做了这个过程的前半段。

### 3.4 为什么当前 BIOS 读盘路径必须留在实模式

当前代码直接通过软中断 `INT 13h` 调用 BIOS 服务，它依赖实模式的 IVT、16 位执行环境和实模式段地址约定。`CR0.PE=1` 之后，`INT` 指令查的是 IDT 而不是 IVT，不能原样继续调用这条 BIOS 路径。因此，**只要选择直接使用当前 `INT 13h` 实现**，读盘就必须放在模式切换之前；这不是说保护模式本身不能读盘。

反过来选：只把现有 `call load_kernel` 挪到 `protected_mode_entry` 之后而不改实现，`INT 0x13` 会去查 IDTR 指向的表——那里仍是复位后的 IVT 基址 `0` 和上限 `0x3ff`，其中的字节并不是合法的保护模式 gate descriptor。门分派会失败，并在当前没有有效异常处理入口的情况下最终 triple fault。

代价：内核只能被读到实模式可寻址的低内存里（见 §3.1），而且我们把对固件行为的依赖固化进了启动路径。

真实系统：**你当年学的 JOS 选的正是另一条路。** JOS 的 `boot/boot.S` 先进保护模式，然后 `boot/main.c` 用自己写的 ATA PIO 驱动（直接读写端口 `0x1f0`–`0x1f7`）把 ELF 内核读进来，完全不用 BIOS。代价是要自己处理状态轮询、DRQ 和 LBA 编码——远超 512 字节的预算，也和本课程"一课一机制"的节奏冲突。值得去读一遍那两个文件，和我们的 `load_kernel` 对比。

### 3.5 为什么 `KERNEL_SECTORS=1`

因为现在载荷正好 512 字节。这是一个**会咬人的**简化。

反过来说，内核一旦长过一个扇区而这个常量没跟着改，`INT 13h` 只会读进前 512 字节，后面全是零。CPU 执行到零字节区域，`00 00` 被解码成 `add [rax], al` 之类的垃圾，然后随机崩掉。这是自制内核里最经典的 bug 之一，而且现象具有极强的误导性——你会以为是链接脚本或跳转写错了。

真正扩容时还有两个坑：`AL` 指定的扇区数不能跨越磁道边界（1.44 MiB 软盘每磁道 18 个扇区），`ES:BX` 也不能跨 64 KiB 段边界。所以多扇区加载通常要写成循环。

### 3.6 为什么 GDT 是 base=0、limit=4G 的平坦段

因为隔离交给分页做，不交给分段做。而且在 long mode 下这不是选择——硬件强制忽略大部分段的 base 和 limit。

历史上 80286/80386 的分段本来是能做隔离的：每个段有独立的 base、limit 和权限，理论上比分页更细。但操作系统生态最终集体选了"平坦段 + 分页"，原因在第 10 课 §1.6 讲过。代价是段不再提供任何保护，全部责任压到页表上——这也意味着页表写错的后果比分段时代更严重。

对照：xv6 用的 RISC-V **根本没有分段这个概念**，只有页表。这恰好说明分段是 x86 的历史包袱，不是操作系统的必需品。

### 3.7 为什么用 debugcon `0xe9` 而不是串口 `0x3f8`

因为它是"零初始化"的输出通道：一条 `out` 指令一个字节，不用设波特率、不用配 FIFO、不用轮询状态位。作为课程的第一个输出（第 3 课），它把前置知识压到了最小。

代价是它**不是真实硬件**。端口 `0xe9` 的调试控制台是 Bochs 引入、QEMU 跟随的约定，真机上什么都不会发生。串口是真实硬件，代价是要初始化 8 个寄存器、要处理发送就绪位。

所以这条输出路径将来必须替换。这也是一个通用模式：教学阶段可以为了"最少前置知识"选一个不可迁移的方案，但要明确记下它是临时的。

## 4. 这个状态还不能承受 C 代码

§2 表格列出的是“已经成立的事实”。下面是“还不成立的事实”——第 17 课引入 C 之前必须知道的缺口。

1. **IDTR 仍指向复位后的实模式 IVT**：base `0`、limit `0x3ff`。这些字节不是 long mode 所需的 IDT gate，本课程也从未执行过 `LIDT`。
   为什么至今没炸？两个条件同时成立：`RFLAGS` 里 `IF=0`（第 9 课 `enter_protected_mode` 开头的 `CLI` 关的，之后再没 `STI`），所以可屏蔽外部中断进不来；而我们的代码从不除零、不访问未映射地址、不执行非法指令，所以也不产生异常。这是**潜伏**，不是安全。注意当前 2 MiB 恒等映射包含地址 0，空指针解引用通常不会触发 `#PF`，而会静默读写物理地址 0；真正访问 `0x200000` 之外的未映射地址、除零或执行非法指令，才会触发 `#PF/#DE/#UD`，并因没有有效 IDT 而最终 triple fault。

   物理地址 0 那里存着什么也值得实测一下：

   ```text
   (qemu) xp /2gx 0x0
   00000000: 0xf000ff53f000ff53 0xf000ff53f000e2c3
   ```

   `f000:ff53` 是 BIOS 的哑中断处理程序入口，也就是说物理地址 0 存的是**仍然有效的实模式 IVT**。所以一次空指针**写**不只是"写到地址 0"，而是直接破坏中断向量表。它现在不咬人，仅仅因为 `IF=0` 且我们再也不用 IVT 了——这正是这类 bug 最难查的形态：破坏已经发生，症状要等很久才出现。
2. **没有 `.bss`**：`kernel/linker.ld` 目前只有 `.text`。C 语言保证未初始化的全局变量为零，这个保证靠加载器或启动代码清零 `.bss` 来实现。现在没人做这件事。
3. **栈没有边界，也没有保护页**：`RSP=0x90000` 是第 9 课硬编码的。它向下增长，一路会经过自由内存、`0x7c00` 的启动扇区代码、最后是 `0x1000`–`0x3fff` 的页表。任何一次过深的递归都会静默踩烂页表，而没有任何机制会报错。
4. **只有一个 2 MiB 恒等映射**：内核、栈、页表全挤在 `0`–`0x1fffff` 里。内核长过 2 MiB 就必须先扩映射。
5. **从没查过内存图**：我们从未调用 `INT 15h AX=E820`，所以完全不知道哪些物理内存可用、哪些是 MMIO 或 ACPI 保留。当前设计应在离开 BIOS 调用环境前收集这份信息；更复杂的 bootloader 也可以通过模式切换 thunk 等方式重新调用固件，但本课程不走那条路。
6. **`KERNEL_SECTORS=1`** 和 **debugcon 不是真实硬件**：见 §3.5、§3.7。

## 5. OS 视角：前 14 课到底为哪些操作系统机制铺了路

这一节回答"这些硬件细节和操作系统有什么关系"。

| 已建立的硬件机制 | 它将支撑的 OS 机制 | 还缺什么 |
|---|---|---|
| GDT 与段选择子 | ring 0/ring 3 特权级边界、系统调用入口 | DPL=3 的 descriptor、TSS |
| 四级页表 | 地址空间隔离、按需调页、写时复制、`mmap` | 每进程一套页表、页错误处理 |
| `CR3` | 进程切换——换 `CR3` 就是换地址空间 | 上下文切换代码、TLB 失效处理 |
| （尚未建立）IDT | 异常、硬件中断、时钟、抢占式调度 | 整个第 3 阶段 |
| `INT 13h` 读盘 | 文件系统、`exec` 加载用户程序 | 真实块设备驱动、缓冲层 |
| ELF + linker script | `exec` 解析用户程序用的是同一种格式 | 程序头解析、重定位 |
| 栈与 `call`/`ret` | 每线程一套栈是上下文切换的前提 | 栈分配、SysV ABI 对齐 |

值得注意的是这张表的右列几乎全部落在"还没做"。前 14 课建立的是**能力**，不是**策略**。操作系统的设计空间在策略里：谁能访问哪块内存、什么时候切换、页不够时换出哪一页。从第 3 阶段起才真正进入这些问题。

## 6. 对照实现

同一个位置，三个系统的不同选择。建议至少读一个的源码，和我们的 `boot.asm` 逐段对照。

**xv6（RISC-V，MIT 6.1810）**——最有启发的一点是：我们的第 7、8、9 课在 RISC-V 上**完全不存在**。没有 A20，没有 GDT，没有实模式，没有段。启动由固件（OpenSBI）完成，`entry.S` 只负责给每个 CPU 设一个栈，`start.c` 在机器模式配置好之后 `mret` 进入监管模式，内核链接在 `0x80000000`，页表是 SV39 三级结构。对照它能清楚看出前 14 课里有多少是 x86 的历史包袱，多少是操作系统的本质。

**JOS（32 位 x86，MIT 6.828）**——你当年学的那个。它和我们前半段几乎一样（A20 + GDT + `CR0.PE`），后半段选择完全不同：自己写 ATA 驱动读 ELF（§3.4）、用双重映射跳高半区（§3.3）、内核链接在 `0xf0100000`。读 `boot/boot.S`、`boot/main.c`、`kern/entry.S` 这三个文件。

**Linux x86-64**——`arch/x86/boot` 的实模式部分用 `INT 15h AX=E820` 拿内存图（我们缺的 §4.5），`arch/x86/kernel/head_64.S` 用 2 MiB 页建早期恒等映射（和我们 §3.2 一致），之后换成正式的内核映射。规模大得多，但骨架能对上。

## 7. 配套阅读

从第 17 课起，实验课都会给这一栏。这次先补齐前 14 课欠下的理论对应：

- OSTEP 第 13 章「The Abstraction: Address Spaces」——第 10 课建的页表是为了实现这个抽象。
- OSTEP 第 15 章「Mechanism: Address Translation」——和第 10 课 §1 的地址转换模型对读。
- OSTEP 第 18 章「Paging: Introduction」、第 20 章「Paging: Smaller Tables」——第 20 章正面回答第 10 课 §2「为什么不是一张巨大的平面表」。
- OSTEP 第 19 章「Paging: Faster Translations (TLBs)」——对应第 10 课 §1.8。
- xv6 book 第 3 章「Page tables」——SV39 三级表与 x86-64 四级表对照。
- Intel SDM Volume 3A 第 6 章「Interrupt and Exception Handling」——第 3 阶段的入口，也是 §4.1 那个缺口的答案。

读这些不是为了做题，而是为了在进入 C 之后，能把“硬件提供什么”和“操作系统用它解决什么问题”两件事对上。

## 8. 把前 14 课压缩成一条因果链

```text
CPU reset
  → BIOS 建立最初的固件环境并读取 boot sector
  → boot sector 在实模式初始化段与栈、借 BIOS 读入内核
  → A20 解除地址回绕，GDT 为保护模式和 long mode 准备代码/数据段
  → CR0.PE + far jump 进入 32 位保护模式
  → PML4/PDPT/PD 建立低 2 MiB 恒等映射
  → CR4.PAE + CR3 + EFER.LME + CR0.PG + far jump 进入 64 位代码段
  → bootloader 跳到 0x10000，执行与该地址一致链接的 ELF 载荷
  → 第 16 课横向对照不同 CPU 架构，分清 x86 细节与 OS 共性
  → 第 17 课由汇编入口按 SysV ABI 调用第一个 C 函数
```

这里最重要的不是记住每个地址，而是看见依赖关系：后一步成立，是因为前一步已经提供了它所需的地址模型、描述符、页表或加载契约。

读完本章后，应该能够用自己的话说明四件事：

1. 从 reset 到 `kernel_start` 的完整控制流，中间谁把控制权交给了谁。
2. 分段和分页在当前系统中各负责哪一段地址转换，为什么 long mode 后几乎只和分页打交道。
3. 为什么开启分页时需要临时恒等映射，以及为什么当前 BIOS `INT 13h` 读盘发生在保护模式之前。
4. 进入 long mode 之后还缺少哪些真正的内核基础设施，尤其是 IDT、`.bss`、受保护的栈、内存图和正式设备驱动。

不需要为本章新增命令或验收结果。把这四点写进 [学习记录](../notes/note-15.md)，就可以进入下一课的跨架构对照。
